# ログイン・本人情報表示

## 目的と範囲

[Issue #53](https://github.com/smofktn/watchbrief/issues/53)で、管理コマンドにより作成した架空Userがログインし、自分のログインIDを確認する。[プロダクト仕様](../product-definition.md#issue-53で最初に確認する画面)を正本とする。

| 項目 | 内容 | 採用状況 |
|---|---|---|
| 画面構成 | 1つのURLで、未ログイン時のフォームと認証後の本人情報を切り替える | 合意済み |
| 未ログイン時 | ログインID・パスワードを入力するフォーム | 合意済み |
| 認証後 | APIから取得した本人のログインIDを表示する | 合意済み |
| 再読込時 | 本人情報APIで認証状態と本人情報を取得する | 合意済み |
| Frontend | Vue 3・TypeScript・Vite・PrimeVue | 合意済み。部品・テーマ・具体版は導入時に確認 |
| URL・配置・装飾 | 下記の構成案。具体URLや幅・色等は未固定 | 提案・未決定 |

会員登録・ユーザー管理画面は作らない。ログアウトは #54、保護URLからの復帰は #55、設定・Reportの取得は #56・#57で扱う。#53の最小表示は、将来の主要ナビゲーションやホーム画面を取り消すものではない。

## 画面構成案

以下は**提案**。項目の役割を示すもので、完成した見た目を固定するものではない。

```text
未ログイン                       認証後
┌────────────────────┐          ┌────────────────────┐
│ WatchBrief         │          │ WatchBrief         │
│ ログイン           │          │ 本人情報           │
│                    │          │                    │
│ ログインID         │          │ ログインID         │
│ [                ] │          │ fictional_user     │
│ パスワード         │          └────────────────────┘
│ [                ] │
│ [ログイン]         │
│ 必要時のエラー表示 │
└────────────────────┘
```

`fictional_user` は表示例。入力されたIDや固定のダミー値を、APIから取得した本人情報の代わりに表示しない。

## 入力と操作

| 要素 | 役割・条件 | 採用状況 |
|---|---|---|
| ログインID | ID条件と正規化は[ユーザーと認証](../product-definition.md#ユーザーと認証)に従う | 条件は合意済み |
| パスワード | 非表示入力。15〜128文字。前後の空白を削らず、大文字・小文字を区別する。入力条件の詳細は同じプロダクト仕様を参照 | 条件は合意済み |
| ログインボタン | 入力値をログインAPIへ送信する | 操作の目的は合意済み |
| ラベル・補完 | 入力欄をラベルと関連付け、IDは `autocomplete="username"`、パスワードは `autocomplete="current-password"` とする | 実装案 |
| キーボード | Tabで入力・ボタンへ移動でき、フォームのEnter送信を使える | 実装案 |
| 処理中 | 状況を文字でも表示し、ログインの二重送信を防ぐ | 実装案。具体表示は未決定 |

ブラウザ側の検証だけで認証・入力条件を保証せず、Go APIでも検証する。Unicodeの文字数をJavaScriptの単純な文字列長と同一視しない。パスワード・Cookie・トークンをコンソールや永続ストレージへ保存しない。

## 状態とAPIの流れ

APIの役割と以下の呼び出し順は**合意済み**。HTTPステータス・JSON等の未合意の詳細は、各API仕様の採用状況に従う。

1. 初回表示・再読込で [`GET /api/me`](../API仕様/get-api-me.md) を呼ぶ。
2. 本人情報が取得できればログインIDを表示し、未認証ならログインフォームを表示する。
3. フォーム送信で [`POST /api/login`](../API仕様/post-api-login.md) を呼ぶ。
4. ログイン成功後、ブラウザによるCookie保存を経て `GET /api/me` を呼ぶ。
5. 取得できた本人のログインIDを表示する。ログインAPIの成功だけで本人情報取得の成功を断定しない。

| 状態 | 表示・操作 | 採用状況 |
|---|---|---|
| 本人情報の確認中 | 確認中と分かる表示。未認証かどうか確定する前に断定しない | 表示詳細は提案 |
| 未認証 | ログインフォーム | 合意済み |
| ログイン送信中 | 処理中表示と二重送信防止 | 実装案 |
| ログイン成功・本人情報取得中 | 取得成功を待つ。入力値を本人情報として表示しない | 取得後に表示する流れは合意済み |
| 本人情報取得成功 | APIのログインIDを表示 | 合意済み |
| 通信・内部障害 | 認証失敗と区別してエラーを表示。障害だけで認証状態を断定しない | 分類は合意済み。再試行操作等の詳細は未決定 |

Cookieはブラウザが送信する。VueからHttpOnlyの認証トークンを読み取らず、[API共通の認証仕様](../API仕様/README.md#共通の認証と秘密情報)に従う。

## 失敗時の表示

入力不正、認証失敗、本人情報取得時の未認証、通信失敗、内部障害の分類と文言は、[プロダクト仕様の表示表](../product-definition.md#issue-53で最初に確認する画面)を参照する。文言の定義をここへ重複して持たない。

入力不正は該当する入力欄の近くへ修正内容を表示する。未知IDと誤パスワードは同じ表示にし、通信・内部障害をパスワードの誤りとして表示しない。APIレスポンスをそのまま無条件にHTMLとして描画しない。

## 未決定事項

- APIの未合意のステータス・JSON・エラーコードとの対応。

## 確認観点

- 初回・再読込で、未認証と本人情報取得成功をそれぞれ正しく表示する。
- ログイン後に本人情報APIの結果が表示され、入力されたIDやダミー値で代用されない。
- 誤パスワードと未知IDの表示を区別せず、入力不正・通信失敗・内部障害を混同しない。
- ログイン成功後に本人情報取得が失敗した場合も、成功表示を先に確定しない。
- 採用する処理中表示、二重送信防止、キーボード操作、狭い画面での表示を確認する。
- パスワード・Cookie・トークンがログや画面のエラー詳細へ出ない。

これらは検証時の観点であり、この仕様書の追加だけで動作確認済みとしない。
