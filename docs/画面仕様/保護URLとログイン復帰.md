# 保護URLとログイン復帰

Issue #55で、[プロダクト仕様](../product-definition.md#保護urlとログイン後の復帰issue-55)の未認証遷移を接続する。既存の認証・画面文言・ログアウトの合意は維持し、具体URLと履歴処理は今回の委任に基づく実装判断とする。

| URL | 役割 |
|---|---|
| `/me` | 認証された本人のログインIDを表示する保護画面 |
| `/login` | 本人情報確認後、未認証ならフォームを表示する |
| `/login?return_to=%2Fme` | ログイン成功と本人情報取得を確認して `/me` へ戻る |
| `/` | 既存入口。`/me` へ正規化して同じ認証確認を行う |
| その他 | 「ページが見つかりません。」と本人情報画面へのリンク。未知URLを保護画面や外部URLとして実行しない |

## 処理と画面の状態

初回・再読込・履歴移動では[本人情報API](../API仕様/get-api-me.md)を使う。確認中は本人情報を表示せず、200で本人情報、401 unauthenticatedでログイン、通信・内部障害でエラーと再試行を表示する。保護画面で障害が起きても未認証と断定してURLを変えない。

ログイン204後も本人情報200を待ってから戻る。認証済みでログインURLを開いた場合も、安全な戻り先または既定の `/me` へ移る。フォーム入力やCookieをURLに入れず、入力IDを本人情報の代用にしない。不要なクエリとフラグメントを除去する。

許可する戻り先は実装済み保護パスの完全一致で、現在は `/me` のみ。外部・相対・プロトコル相対・逆スラッシュ・不正な符号化・重複return_to、`/login`・`/api/`・未知ルートを拒否し、`/login` と既定の戻り先を使う。許可パス内の任意クエリ・フラグメントも現在は受け付けない。後続画面の追加時に必要な形式だけをテストとともに増やす。

## 履歴とログアウト

認証による画面遷移は現在の履歴を置換する。ブラウザの戻る・進む（popstate）とBFCacheからの復帰では本人情報を再確認し、以前の画面の応答で本人情報を復活させない。

ログアウト開始時は即時消去と `/login` への遷移を行う。完了未確認中は履歴移動でも本人情報を再取得せず、[既存の再試行](ログイン・本人情報表示.md#ログアウトissue-54)を維持する。204後に空フォームを表示する。通信・内部障害からの再試行はログアウトAPIだけを呼ぶ。

## 確認観点

- 保護URLを直接開く→ログインURL→成功後の本人情報と元パス、再読込。
- 戻り先なし・未知・外部・符号化・重複指定・API/loginへの指定で外へ移らず循環しない。
- 失効後の401と、通信・内部障害の500を区別する。
- ログアウト未確認時の履歴移動で本人情報を戻さず、再試行できる。
- 遅れた本人情報・ログイン応答を別画面へ適用しない。秘密値をURL・ログ・永続ストレージへ入れない。

画面遷移のためにGo APIの認証・Cookie・CSRF契約を変更しない。Report詳細への適用は #57で確認する。本番nginxのSPA fallback・TLSは #21で実環境を検証する。

Issue #57で `/reports` と `/reports/{正規ULID}` を保護パスへ追加する。詳細URLからログイン後に同じReportへ復帰する。[保存済みReportの取得](保存済みReportの取得.md)を参照する。
