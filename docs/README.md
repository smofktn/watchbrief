# WatchBrief ドキュメント

このディレクトリには、WatchBriefの仕様、論理設計、初期インフラ・運用設計を置く。

## 文書の役割

| 文書 | 役割 | 決めること |
|---|---|---|
| [プロダクト仕様](product-definition.md) | 仕様の正本 | 利用者体験、画面、機能、MVP範囲、主要な業務ルール |
| [システム設計](system-design.md) | 論理アーキテクチャと初期インフラ・運用設計 | コンポーネントの責務、生成処理、配置・権限境界、監視、更新・復旧手順 |
| [ドメインモデル](domain-model.md) | アプリのドメイン設計 | 概念、責務、業務ルール、状態遷移 |
| [DB設計](database-design.md) | 論理スキーマ案 | テーブル、ER図、カラム、外部キー、制約、初期インデックス |
| [技術選定の前提](technical-direction.md) | 選定時の判断材料 | プロジェクト目的、重視する性質、候補、未決定事項 |
| [作業計画と将来候補](work-plan.md) | 作業の追跡先と順序案 | 初期実装・構築への引き継ぎ、将来候補のIssue一覧、Issue #1の残りと実装開始までの見通し。候補の採用決定とは区別する |

仕様と設計が食い違う場合は、プロダクト仕様を優先する。合意した仕様変更は、まずプロダクト仕様へ反映し、影響するシステム設計、ドメインモデル、DB設計も同じ変更で更新する。

初期構成をざっと確認する場合は、[Issue #11の範囲と全体像](system-design.md#issue-11の範囲と初期構成の全体像)を参照する。[構築・運用の設計案](system-design.md#構築運用の設計案)では、合意済みの構成を前提に、採用前の具体方式と手順をまとめている。アプリ実装・AWS構築は設計Issueの対象外とする。

認証と非公開データの扱いは[Issue #1の設計](system-design.md#issue-1の認証公開境界秘密情報設計)を参照する。Cookie・CSRFの方式選定は実装時、ログイン失敗制限・認証専用記録はMVP後、内部宛てのSSRF対策は初期MVPと区別している。後続Issueと実装開始までの順序案は[作業計画](work-plan.md)にまとめる。

## まだ決めないこと

現在は論理設計の段階であり、次の技術選定は未決定である。

- Vue・Goの具体バージョン、周辺framework、runtime設定、package manager
- Ubuntu Server LTSの具体バージョン・AMI・CPUアーキテクチャ、更新・再起動手順
- PostgreSQLのバージョン、将来のRDSのDBエンジン（Auroraを含む比較）、サイズ、可用性構成、物理データ型、ORM、migration方式
- Job queueとworkerの実装方式
- AIサービスと呼び出しライブラリ
- 専用VPCの作成手順・IaC方式、東京リージョンのパブリックサブネットに置く初期EC2のAZ・IP・経路などの具体設定、DB接続・保存方式、nginx・systemdの具体設定、ドメイン・HTTPS、手動デプロイの具体手順と将来の自動化方式
- 初期SSHの実際の接続元IP・鍵の具体仕様と管理・権限、Session Managerへの移行時期・具体手順
- AWS管理鍵で暗号化するOS用・DB用EBSの容量・種類・保存場所・マウント・権限、OS用EBSの削除方針とDB用EBS保持後の管理・削除手順
- 後で決めるドメイン名・アプリ別取得か親ドメイン共用か・登録事業者・DNS・予算と更新方針、Elastic IPとの関連付け
- 将来のコンテナ化とECSなどへの移行時期・条件、実行方式
- timeout、heartbeat、監視、バックアップの具体値

初期DBはPostgreSQLを採用し、EC2へ同居させ、将来RDSやECSなどへ段階的に移す方針に合意している。[システム設計の移行の見通し](system-design.md#段階的な移行の見通し)で、合意した方向性と未合意の設計案を区別している。

未決定事項を、実装上の都合だけで仕様として固定しない。候補、理由、影響を整理して合意した後に文書へ反映する。
